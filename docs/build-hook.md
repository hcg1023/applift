# 变更提案：构建命令钩子（build-hook）

> 状态：**评估结论「暂缓」（2026-10-24 决定），本文存档以便后续重启**。
> 前置：`docs/bump-semantics.md`（版本声明与封板语义）。两者正交：版本语义解决"判断正确"，构建钩子解决"步骤数量"。

## 1. 需求

### 1.1 问题

一次原生迭代目前是 3 条命令 + 1 次人工等待：

```bash
applift beta harmony --bump          # 判定原生 → 声明 4.1.0（写文件 + commit）
npm run test:harmony:native          # 构建测试包 4.1.1000（10–30 分钟）
applift beta harmony --delivery native   # 发到 AGC
```

两个痛点：

1. **步骤多且顺序有隐含约束**（忘记重建 → 产物版本校验会拒发，虽然安全但打断心流）。
2. **versionCode 有两个写入者**：`applift version bump` +1，项目构建脚本（qy-driver 的 `scripts/build-test.js`）每次出包再 +1。语义一致（都只单调递增），但归属分散。

### 1.2 历史教训（为什么当年否决"接管构建"）

v1 的失败点**不是"applift 跑了构建命令"**，而是"applift 自以为知道每个框架/渠道该怎么构建"：`FrameworkAdapter` 带 `buildCommand`、按渠道拼参数。遇到签名域差异（蒲公英的 `internaltesting.hap` 与 AGC 的 release `.app` 是两套证书、两个产物）就算不出来，团队只能绕过 applift 手工构建，`可信任的自动化` 一旦断裂就不可恢复。

因此本提案**只讨论不透明命令钩子**：applift 把命令当黑盒字符串执行，绝不解析、绝不按渠道拼参数。这从根上避开了 v1 的失败模式。

### 1.3 目标（若实施）

1. 原生迭代压成 2 条命令（甚至 1 条）：`applift beta harmony --bump --build`。
2. versionCode 由 applift 独占分配：构建前写、构建后保留。
3. 保持 core 零框架知识：命令是配置里的不透明字符串。
4. 保证"构建前后版本事实一致"：构建前注入孪生版本名，构建后按需还原，中断也必须还原。

### 1.4 非目标

- 不做 framework 感知的构建编排（不回到 v1）。
- 不建模"平台 × 渠道"构建矩阵：多渠道多产物由**一条命令一次出全**（qy-driver 的 `test:all` 已是此形态）。
- 不接管签名、证书、渠道变体（仍属项目域知识）。
- 不改变 OTA 路径：热更不构建、不触发钩子。

## 2. 设计（若重启）

### 2.1 接口

```ts
// applift.config.ts
build: {
  /** 不透明命令；applift 只 spawn，不解析、不拼参数。仅原生判定时执行 */
  command: "npm run test:all",
  /** 可选：超时（分钟），默认 60 */
  timeoutMinutes?: number,
  /** 可选：构建前需要注入的版本策略（缺省沿用 version.beta） */
}
```

入口：

```bash
applift beta harmony --bump --build      # 判定原生 → bump → 执行 build.command → 校验 → 发布
applift beta harmony --build             # 已有声明版本，只构建+发布
```

### 2.2 流程

```
判定 OTA        → 不发构建，直接发 ppk
判定 原生·需 bump → [bump + commit] → 注入孪生版本名 → spawn build.command
                → 等待退出（流式转发输出、超时、Ctrl-C 透传）
                → 还原工程 versionName（保留 versionCode）
                → 探测产物 + 校验产物版本 == 孪生体
                → 发布（AGC/pgyer）
判定 原生·已声明 → 跳过 bump，直接注入 + 构建 + 发布
```

### 2.3 三条硬契约（缺一即退回双写）

1. **构建脚本删净版本逻辑**：项目侧 `applyBuildVersions` / `betaVersionName` / `assertBetaConfigMatches` / `restore` 全部删除，构建脚本退化为纯构建（只产产物，不碰版本）。否则 applift 与脚本会各写一次。
2. **applift 永不解释命令**：不新增任何"按渠道/签名域拼构建参数"的能力。参数差异要么写进命令字符串，要么由项目脚本内部按环境变量决定。这是 v1 教训的唯一复发点。
3. **产物契约**：命令成功返回后，每个待发布 (渠道, 扩展名) 的产物必须已存在且内嵌版本 == applift 期望值；否则拒绝发布。多渠道多产物由命令一次出全。

### 2.4 不变量 1 的改写文本（提案）

> **不接管构建（收紧版）**：构建是项目域知识（签名/证书/渠道变体/自定义脚本链）。applift 仅允许 spawn **项目配置中声明的不透明命令**（`build.command`），且：
> (a) 不得生成、拼接、推断构建参数；
> (b) 不得感知框架/渠道的构建差异；
> (c) 产物仍是唯一发布入口，命令执行后必须通过版本校验。
> 禁止任何"framework 感知的 buildCommand"字段或等价能力（v1 实证失败）。

### 2.5 与版本语义的关系

依赖 `bump-semantics` 先落地：

- 构建钩子只在"原生·需 bump / 已声明"两态触发；OTA 不构建。
- 版本声明仍是构建前置条件（孪生体由声明版本派生）。
- 锚点机制保证"bump 后再次 beta"不会重复 bump，钩子不会陷入"每次 beta 都 bump + 构建"。

## 3. 风险

| 风险           | 说明                                                        | 缓解                                                        |
| -------------- | ----------------------------------------------------------- | ----------------------------------------------------------- |
| 构建生命周期   | 10–30 分钟持有子进程；流式输出、超时、退出码透传            | 统一 `spawn` 封装；超时可配；输出直通                       |
| 中断还原       | Ctrl-C / SIGTERM 时必须还原 versionName（versionCode 保留） | 复用 build-test.js 的 signal handler 语义，进 core 并加测试 |
| 失败诊断       | 构建失败信息在项目脚本输出里，applift 无法人话化            | 原样转发 + 退出码；不试图解释                               |
| 参数泄漏       | `--skip-bundle` / `SIGNING_CONFIG` 等参数被迫进入命令字符串 | 命令字符串由项目维护；applift 不解析，文档示例              |
| 构建矩阵       | 多渠道多产物可能诱发"按渠道调用多次"                        | 契约强制"一次出全"；applift 不为渠道分别调用                |
| 不变量回退风险 | 一旦出现"applift 自己决定构建参数"的路径，v1 会重演         | 不变量 1 收紧文本 + review checklist                        |

## 4. 结论与重启条件

**结论：暂缓（2026-10-24）**。理由：

1. 版本语义（正确性）优先，构建钩子只是体验优化。
2. 当前只有一个真实用户、一个构建脚本，3 步流程可接受。
3. 引入构建生命周期会显著扩大工具职责面（mini-CI），维护成本与失败模式都上升。

**重启条件（满足任一）**：

- 原生迭代频率显著上升（例如每周 ≥1 次），3 步流程成为高频摩擦；
- versionCode 双写导致过真实事故（同号、回退、烧号过快）；
- 第二个真实项目接入，且构建步骤差异大（证明"不透明命令"确实能泛化，而不是为一个项目定制）。

**若实施，验收标准**：

| #   | 验收项                                                                |
| --- | --------------------------------------------------------------------- |
| 1   | `beta --build` 在原生判定下 bump → 构建 → 发布全流程通过（mock 命令） |
| 2   | OTA 判定下**不执行** build.command                                    |
| 3   | 构建失败 / 超时 / Ctrl-C 后 versionName 还原、versionCode 保留        |
| 4   | 产物版本与期望不符时拒绝发布                                          |
| 5   | 不声明 `build.command` 时行为与现在完全一致（零侵入）                 |
| 6   | 不变量 1 改写 + AGENTS.md 更新 + 全量测试绿                           |
